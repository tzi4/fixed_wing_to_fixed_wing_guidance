# 3.5 Flash guidance fusion: architecture and tuning plan

This historical design note compares five guidance implementations and
records the proposed 3.5 Flash fusion. Architectural assessments and tuning
suggestions are design claims. They do not establish flight validation of
the fused controller. The archived implementation is
[`tzi_3.5_fused.py`](../guidance/tzi_3.5_fused.py).

## Source implementations

The TZI family (`tzi.py`, `tzi2.1.py`, and `tzi_final.py`) separates vision,
telemetry, and command transmission into threads. A Redis listener updates
the latest bbox, vision processing runs at 30 Hz, and `TestCommander` sends
commands at 5 Hz. `tzi_final.py` converts pixel error to angular error with
`math.degrees(math.atan(pixel_error / fx))`, expressing controller input in
degrees. Correct intrinsics remain necessary when resolution or field of
view changes.

`tzi.py` adjusts `TRIM_THROTTLE`, while `tzi2.1.py` and `tzi_final.py` use
MAVLink command 178, `MAV_CMD_DO_CHANGE_SPEED`. The reviewed `tzi2.1.py`
contained fixed targets `self.test_heading_deg = 0.0` and
`self.test_alt_m = 40.0`. The reviewed `tzi_final.py` also overrode the
computed sender values with heading 0.0 and altitude 40.0. These overrides
must be accounted for when interpreting tests because the calculated
heading and altitude corrections were not sent.

The Emir family (`initial_camp_emir.py` and `goat_gimbal.py`) provides explicit
turn-rate and climb-rate control. Reported ranges are 0.85–7.5 deg/s and
0.3–5.0 m/s. A speed slew limit of 1.0 m/s per second constrains TECS
transients. An exponential moving average with alpha 0.05 filters the
PID derivative. `FlightLogger` records 59 CSV fields.

The queue-driven main loop couples calculation, logging, and sending, so
delays in that loop can affect control timing. In the reviewed
`goat_gimbal.py`, heading and altitude sends were commented out and only
a fixed 20 m/s airspeed request remained active. Flight experience with
that source does not validate all of its calculated control outputs.

## Fusion design

The proposed controller combines the following elements:

1. The threaded structure of `tzi_final.py`.
2. Virtual-gimbal back-projection/reprojection and angular errors
   `stab_error_x_deg` and `stab_error_y_deg`, using focal lengths derived
   from camera calibration or HFOV.
3. Dynamic heading-rate and altitude-rate control, filtered derivatives,
   and integral windup limits.
4. Coverage-based airspeed PID with a 1.0 m/s² slew limit.
5. The 59-field `FlightLogger` schema for offline analysis.
6. Target-loss handling that retains the latest commands for the first
   5 s, then clears PID integrals and requests the current heading and
   altitude. Fixed simulation overrides are excluded from the fused sender.

These are the recorded design choices. Failsafe behavior and control
limits require independent validation before use on an aircraft.

## Offline tuning procedure

Begin with conservative gains, for example `Kp_heading = 3.0`,
`Kp_alt = 1.5`, zero integral gain, and derivative gain 0.1. Record command
and measured response, including delay and rise time, with `FlightLogger`.

Use `cmd_heading_deg` as an input and `yaw_deg` as the corresponding
measured response. Fit a first-order model with delay:

`G(s) = K·exp(−τs) / (T·s + 1)`

Here K is the gain, τ is the delay, and T is the time constant. Evaluate
candidate P, I, and D gains offline in Python or MATLAB, for example with
the integral of time-weighted absolute error (ITAE). Transfer selected gains
to the archived controller only after checking the model's limits, then
validate in simulation and controlled flight. The proposed procedure does
not itself demonstrate stable tracking.
